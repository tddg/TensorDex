§ 1

Setup: one hub, four ways to download it

The corpus is a delta-compressed TensorDex hub built from the live store with the full paper pipeline (TensorSketch → FlexSplit attach at 0.70 → TensorX deltas, zstd L1): 9 fine-tunes in three families — llama-3.2-3B (~1.7 GB each), Qwen2.5-7B (~15.2 GB), gemma-2-9B (~18.5 GB) — stored at compressed_eval/ next to the uncompressed dedup-only store at tensordb/. 3,026 of 3,456 tensors are TensorX deltas; every download in this study re-verified every tensor against its content hash.

Each model was downloaded under four regimes, every run fully traced (per-request first-byte and body timing, decode timing, resource sampling):

RegimeWhat the client doesWhat it models
Direct S3GETs raw tensors from the uncompressed dedup storetoday's deployment (no compression)
Client-side decodeGETs the delta closure (deltas + transitive bases), decodes TensorX locally"smart client" pulling the compressed hub
Server, cold cacheGETs plain tensors from a reconstruction cache that must first fetch + decode from S3backend reconstruction, first request
Server, warm cacheGETs plain tensors already materialized on the cache server's diskbackend reconstruction, hot model

The server regimes run against two services deployed for this study — a metadata server (per-model manifest and per-tensor delta closure over the hub catalog) and a colocated reconstruction cache server (S3 closure fetch → TensorX decode → hash verify → disk cache → serve). The client sees plain bytes: read amplification is exactly 1.0 by construction, and the closure cost moves server-side.

§ 2b · added 2026-08-03

Serving tier, round two: the i4i deployment

Everything in §2's server rows came from a prototype: both servers running on the same t3.xlarge as the client, caching on gp3 EBS. The production-shaped tier now exists — a dedicated i4i.2xlarge running the real serving stack — and the full 9-model matrix was re-run against it (18 runs, rep 0 cold / rep 1 warm, all byte-exact, zero client retries). The two campaigns are reported side by side, never merged: they differ in topology, medium, serving code, and cold protocol.

t3 prototype OLD · Stage 1

  • Topology: metadata (:8701) + cache (:8702) on the same t3.xlarge as the client — loopback, no network hop, 4 vCPU / 16 GB shared between client and servers.
  • Cache medium: gp3 EBS (~50–130 MB/s, shared with the client's own shard writes); page cache rescued only the 3B models.
  • Cold path: Python http.server; per-tensor demand materialization, sequential chain fetch — ~60% of bandwidth idle.
  • Cold protocol: /admin/clear before each model; every cold run started from an empty cache.

i4i deployment NEW · 2026-08-03

  • Topology: dedicated i4i.2xlarge (8 vCPU / 64 GB / 1.8 TB instance-store NVMe / 12.5 Gbps); t3.xlarge client pulls over the VPC. nginx cache front :8700, metadata :8701; materializer loopback-only.
  • Cache medium: instance-store NVMe behind nginx sendfile + X-Accel-Redirect — Python never copies hot bytes.
  • Serving code: the server/ package (plan Phases 0–2): precomputed immutable manifests + ETag, singleflight materializer, whole-closure pipelining, watermark evictor.
  • Cold protocol: one full clear, then natural first touch driven by the client's 10 parallel demand streams — no /v1/warm anywhere (see purity note below).

Anchor against the incumbent: the same models from huggingface.co

Measured 2026-08-03, one model per family, from the same t3 client: hf download --include "*.safetensors*" with huggingface_hub 1.26.0 and the hf_xet backend (HF's current default — parallel chunked transfer with chunk-level dedup), fresh cache, weight files byte-identical in size to our logical bytes. Three observations: (1) the i4i tier beats the real Hugging Face hub in every measured regime except one tie (Egida cold): warm wins 1.2× on big models and 7× on the 3B, and even cold demand-miss reconstruction matches or beats it. (2) HF runs below this client's NIC — 116–118 MiB/s on the 7B/9B against the 136–143 our warm path pins, and just 66 MiB/s on the single-file 3B adapter. (3) Xet's wire dedup is real but modest here: 8–10% fewer bytes on the wire than written to disk, vs the 35% our store saves at rest — transfer-layer and storage-layer dedup are different layers, and a hub could stack both. Caveats: single rep against a public CDN whose performance varies; a sanity anchor, not a controlled A/B. Raw numbers: eval/results/hf_baseline.json.

What moved, and where the bottleneck went

Cold: 2.1–2.9× faster on 7B/9B — direct-S3 parity

Demand-miss materialization driven by 10 client-parallel streams runs 93–155 MB/s (prototype: 45–65). Woona's 26.9 GB depth-2 closure materializes in 137 s (was 415 s). SimPO's shallow closure materializes faster than the client NIC drains it — cold equals warm, which is the end state a serving tier wants: reconstruction fully hidden behind the wire.

Warm: 2.0× faster — and the bottleneck left the server

Every big-model warm run pins at 136–143 MB/s, the t3 client's sustained NIC rate; the 3Bs (served during burst credits) hit 432–459 MB/s, and the on-box smoke hit 878 MB/s. The cache tier is no longer measurable from this client — finding its true ceiling needs Stage 3 concurrent clients or a bigger-NIC client.

The soft spot: llama-3B cold, 9.9 / 28.4 / 43.2 s

Three near-identical 1.7 GB models, all ≥99.7% miss-served — so not cache pollution. The 3B workload is latency-bound (~400 tensors at ~4.5 MB average; per-miss round trips dominate, nothing pipelines). The 3× spread needs server-log correlation; suspects are first-run effects (the 28.4 s run started seconds after a materializer restart) and the per-run spill isolation re-materializing the >512 MB shared embedding per chain. Candidate fix: tid-scoped, refcounted spill.

Metadata: 9–13 ms

Manifest resolve against precomputed immutable manifests: 9–13 ms (prototype: 26–122 ms; local whole-catalog SQLite: 250–380 ms). Warm-hit TTFB through nginx: 2.9–4.9 ms. Cold TTFB p50 is now the cleanest per-run indicator of materialization queueing: 24 ms (SimPO) to 2.4 s (Tong-star).

Cold-run purity: the overlap discovery

The relaunch protocol assumed no closure shares a tid across models — so natural first-touch cold runs could not contaminate each other. Post-run measurement falsified the premise: closures overlap heavily within families (Woona's closure contains 265 of SimPO's 464 params; the Qwens share 100+ closure tids pairwise; even chat-doctor/GSOC share 11). Materialization caches closure ancestors, so later cold runs found some tensors resident. Measured impact via client TTFB (<50 ms ⇒ hit): small — the shared tids are overwhelmingly norms and biases. Pre-cached bytes: 7.2% for SimPO, ≤2.5% for everything else. The conclusions stand; the per-model table above carries the annotation instead of the runs being discarded.

The "contamination" is a feature wearing a caveat's clothes. Cross-model ancestor sharing at the origin tier is exactly what a DAG-aware cache should exploit — serving Woona pre-warms SimPO. It is the serving-side face of delta-graph locality, the phenomenon dag_value eviction scores (contribution C4), and it deserves a designed experiment — serve the base, time the fine-tune — rather than an accidental appearance in a cold protocol.

§ 3

Bottlenecks, ranked

The ranking as measured in Stage 1 (t3 era), with each item's fate on the i4i tier marked inline. Net effect: items 3 and the cold half of the story are gone; the NIC is now the wall everywhere.

  1. Client NIC line rate (~145 MB/s)

    Direct S3 saturates it; its end-to-end time is pure transfer. Nothing beats it on a cold client unless the bytes on the wire actually shrink — and mostly they don't (next item). i4i: unchanged, and now it caps the server path too — warm and fast-cold serving both pin at the client NIC; the tier has headroom this client can't consume.

  2. Delta-closure read amplification

    Client-side pulls transfer deltas plus all transitive bases: amplification runs 0.52 on near-twin llamas to 1.45 on Woona, whose depth-2 chains move 26.9 GB for an 18.5 GB model. Chain depth converts storage savings into wire cost; only genuinely delta-heavy models (Bangla, 0.81) win end-to-end.

  3. EBS disk throughput (~50–130 MB/s, shared)

    The sleeper. Warm big-model serving is disk-bound at ~75 MB/s (server read contending with client shard writes) — slower than just hitting S3. Only models that fit page cache see RAM-speed serving (~700 MB/s). Cold reconstruction is worse still (45–65 MB/s): per-tensor materialization leaves ~60% of the NIC idle, with time-to-first-byte up to 2.6 s while a chain decodes. i4i: eliminated — NVMe + sendfile serves ≥878 MB/s on-box; big-model cold runs 93–155 MB/s; EBS keeps only the catalog. Residue: latency-bound small-tensor cold (§2b).

  4. TensorX decode CPU — never the bottleneck

    Server-side, fetch:decode is ≈ 7:1 on big tensors (2.3 s vs 0.33 s p50). Client-side, ~38 s of decode CPU on a 138 s run overlaps the fetch; it surfaces as effective network dropping 145 → ~97 MB/s, not as added wall time.

  5. Metadata — solved by serving it

    Per-model manifest over HTTP: 26–122 ms. Local SQLite over the 1.35 GB whole-catalog copy: 250–380 ms. Warm-hit TTFB through the cache: 1.2 ms. With per-model manifests, the metadata tier is nowhere near any critical path — the 40× size gap between catalogs (32 MB vs 1.35 GB) is the real argument against shipping the catalog to clients. i4i: 9–13 ms with precomputed immutable manifests — solved twice over.

§ 4

Production design: control plane / data plane

TensorDex today has no metadata service — the catalog is a whole-hub SQLite file stored as an S3 object, and the stock S3 backend cannot decode deltas. The production shape we converged on separates a thin control plane from an S3 data plane, with reconstruction as an optional tier:

Control plane

  • resolve(model) → manifest: the full delta closure — keys, sizes, dtypes, base graph — in one response. Immutable per version, CDN-cacheable. Per-model manifests replace ship-the-whole-catalog.
  • begin_upload / commit_upload: blobs first (orphans are harmless), metadata commit last, in one transaction; idempotent retries via content addressing.
  • Presigned URLs keep the metadata tier out of the byte path entirely — it only ever moves kilobytes.

Data plane & background

  • Content-addressed blobs on S3; per-tensor hash verify end-to-end (free integrity — keep it).
  • Async compactor: FlexSplit pairing + TensorX encode, never blocking upload, never rewriting in place — write new object, flip pointer, GC the old.
  • Refcount GC over the delta DAG with a grace period, plus a metadata↔S3 auditor (HEAD sampling).
  • Distribution chains capped at depth 1; deeper chains belong in cold archival tiers behind reconstruction.

"S3 is replicated, so no extra fault tolerance" — rejected, with evidence

S3 protects bytes, not cross-object invariants — and TensorDex's value lives entirely in those invariants. Our own bucket is the case study:

Metadata is the durability crux

Content-addressed keys are opaque hashes: lose the metadata and 72 TB of perfectly durable blobs become garbage. The metadata tier needs replication, backups, and point-in-time recovery more than the blobs need anything.

Half-finished ingests leak

~1M orphaned blobs (~32 TB — 44% of the bucket) from partial ingests. The fix is write ordering plus mark-and-sweep GC, not replication.

The inverse failure is worse

One model sat 'ready' in metadata with 417 of 464 blobs already garbage-collected. With deltas this sharpens: a base may serve other models' deltas, so deletion must be refcount-driven over the delta DAG — never per-model.

In-place rewrite races readers

The AE pipeline overwrites a raw blob with its delta, then updates the row — fine offline, a torn read under concurrent clients. Compaction must be copy-on-write with a transactional pointer flip.

§ 5

The reconstruction tradeoff: client-side vs backend

The instinct "users will prefer backend reconstruction" is right for one population and costly for the other. The measurements sharpened the tradeoff into three facts:

Decompression is not the cost. TensorX decode is ~8.5 s of CPU against a 348 s cold download. The real tax of client-side decode is the dependency closure — which is why the Docker precedent doesn't transfer: per-blob zstd is self-contained; delta-vs-base is not.

Who already has the bases decides the winner. A cold one-shot client has nothing, pays the closure, and can't reuse it — backend reconstruction strictly dominates for them, and it's transparent (plain safetensors, existing tooling works). A warm fleet pulling successive fine-tunes of one family holds the bases locally and pays only delta bytes for each new model — ~10× less last-hop traffic than any backend scheme, which must always ship full logical bytes. Backend reconstruction permanently forfeits that win because it destroys the delta structure before the bytes cross the network.

A reconstruction cache is really tiered storage. Decoded hot models at the edge, compressed cold models in S3 — the Xet/CAS shape. Deploy it on hardware whose serving medium beats the client's S3 path: this study's gp3-EBS cache helps 3B models (page cache, 4× faster) and hurts 15–18 GB models (1.8× slower than direct S3).

Production answer: offer both, per client. resolve() returns either presigned URLs for reconstructed artifacts via the cache tier (the default — transparent, cold-client friendly) or the delta closure for smart clients that advertise which bases they already hold and receive only the missing keys. The smart path degrades gracefully to the plain one. Priority order per the study: performance evaluation first (done — this report), full tradeoff quantification next (Stage 2 measures the warm-fleet delta win).

Updated verdict (2026-08-03, §2b): on real serving hardware, backend reconstruction dominates client-side decode in every measured regime, and matches or beats uncompressed direct S3 everywhere except cold small models — while the store keeps its 35% size reduction. Client-side decode remains the right opt-in for warm fleets with local base caches, and the fallback when no serving tier is nearby.

§ 6

Engineering lessons from the measurement clients

Three OOM kills during this study traced to the same pattern: a fast producer (S3 or the cache server) feeding a slow consumer (decode, hash, EBS writes) through implicit buffering. A budget valve that let fetches "trickle" past the cap accumulated completed buffers without bound; a list of futures silently retained every fetched buffer until the loop ended; depth-2 delta chains stacked three ~1.8 GB decoded tensors on a 16 GB host.

The fixes generalize to any streaming tensor client: explicit, end-to-end byte-budget back-pressure — admission control where only the head-of-line blob may exceed the budget, dropping each buffer reference at consumption, refcounted decoded-base caches with disk spill, and preallocated output shards written by offset. Peak client RSS fell from 15 GB (killed) to 5.4 GB (stable) with no throughput loss. One format gotcha worth recording: per-tensor codec metadata lives as a JSON string under __metadata__[name] inside each blob — missing item_size there decodes float32 deltas with the wrong byte-plane width, which the end-to-end hash verify caught.

The i4i campaign added the dual of the buffering lesson: unbounded waits. A server-side abort left a response stream open forever; the client had retries but no read timeout, and the head-of-line gate faithfully queued the entire download behind one dead request. Every streaming client needs a silence timeout plus idempotent re-issue — content addressing makes the retry free. Two more, from the server side: correctness fixes have throughput prices (per-run spill isolation fixed an unlink race but may re-materialize shared spilled bases per chain — the sharing-vs-isolation choice wants a tid-scoped, refcounted resource, not a blanket rule); and protocol premises need measurement, not agreement — "no closures overlap" was believed by everyone and false, caught by TTFB distributions in the traces (§2b).

§ 7

FAST'27 research scope: the hub between TensorDex and TDN

Three lines of work now share this territory, and the FAST'27 paper is defined by the layer the other two assume but don't build. TensorDex (SOSP'26) is an encoder — offline, single-writer, no users. TDN is a delivery network — geo-distributed edges caching reconstructed or compressed tensors, owning placement, egress minimization, and user-perceived delivery performance. Neither is a hub that real users upload to, delete from, and download from concurrently.

Thesis: in a derivative-aware store, every ordinary hub operation becomes a DAG transaction. Upload, delete, compaction, and garbage collection — trivial in a plain object store — acquire cross-object invariants once tensors reference other tensors. The system that maintains those invariants under concurrency and failure, while still serving reads, is the missing layer between the encoder and the delivery network.

C1 · Transactional lifecycle over the delta DAG

Upload commit (blobs first, one metadata transaction last, idempotent by content address); refcount GC where a base may serve other models' deltas — deletion is a DAG operation, never per-model; copy-on-write compaction with transactional pointer flips. Motivated by live-bucket forensics: 44% of 72 TB orphaned by partial ingests; 'ready' models whose blobs were GC'd.

C2 · Online ingest + storage-form scheduling

Synchronous dedup at upload; sketching and pairing async; the hub decides when and what to (re)compress and each tensor's origin form — hot raw or shallow, cold deep-chained — under a bounded local working set. The storage-form residue of the measured "storage-optimal ≠ distribution-optimal" tension; placement itself is TDN's.

C3 · The DAG-aware interface as narrow waist

Immutable per-model manifests, closure queries, have/want negotiation (/v1/plan), reconstruct-on-read. FAST defines the interface and shows a plain client using it; TDN consumes it. This makes the two papers load-bearing for each other instead of overlapping.

C4 · DAG-weighted origin caching — pending boundary

Eviction where a cached base is worth the summed re-materialization cost of its resident dependents; A/B against LRU on the same trace. Claim only if TDN's edge-caching sections don't claim graph-aware eviction — needs a written boundary agreement with the TDN authors early (shared reviewer pool).
